# Pinned, mutually compatible stack for CINECA Leonardo (verified July 2026).
#
# Leonardo Booster imposes TWO hard constraints that together eliminate every
# recent vLLM wheel:
#   1. GPU driver 535.x => CUDA 12 only. A CUDA-13 build fails to import with
#      "libcudart.so.13: cannot open shared object file" (or, for torch,
#      "The NVIDIA driver on your system is too old (found version 12020)").
#   2. RHEL 8 => glibc 2.28. A wheel tagged manylinux_2_31 / 2_35 has no usable
#      build, so pip falls back to a source build -> "CUDA_HOME is not set".
#
# vLLM's own compiled extension (vllm._C) links a specific libcudart, and the
# published wheels line up like this (x86_64):
#   * vllm >= 0.20  : manylinux_2_28 (glibc ok) BUT link libcudart.so.13. no.
#   * vllm 0.12-0.19: link libcudart.so.12 (good) BUT manylinux_2_31 (glibc). no.
#   * vllm 0.11.x   : manylinux1 (any glibc) AND link libcudart.so.12. YES.
# vllm 0.11.2 pins torch 2.9.0, whose DEFAULT PyPI wheel is already the
# CUDA-12.8 build (nvidia-cuda-runtime-cu12==12.8.90, manylinux_2_28) — it runs
# on the 535 driver via CUDA minor-version compatibility (needs driver >= 525).
#
# vLLM 0.11.2 is outside TRL 1.8.0's supported window, so we step TRL down to
# 1.2.0 (supports vllm 0.11.0-0.18.0) and transformers to the 4.57.x line
# (vllm 0.11.2 requires transformers <5; TRL 1.2.0 requires >=4.56.2). The GRPO
# training/eval/reward code in this repo is verified to run unchanged on this
# stack (config keys, dataset-column forwarding to reward funcs, checkpointing,
# and the `trl vllm-serve` CLI used by slurm/train_server_mode.slurm).
#
# Do NOT bump past this until CINECA upgrades the driver to >= 580, which would
# unlock the CUDA-13 wheels (vllm >= 0.20 + torch 2.11 + trl 1.8).
#
# Install on a Leonardo LOGIN node (internet) via scripts/setup_leonardo.sh.
trl==1.2.0
vllm==0.11.2
torch==2.9.0            # PyPI default wheel = CUDA 12.8 (libcudart.so.12)
transformers==4.57.6
datasets==5.0.0
accelerate==1.14.0
pyyaml
